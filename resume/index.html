햇배달 — 배달 기사용 실시간 주문 처리 앱

기획 2025.02 · 개발 2025.05~11 · 운영 ~2026.07 | iOS 단독 | Swift · SwiftUI · Swift Concurrency · SSE

큐마켓을 통해 들어온 주문을 마트 배달 기사가 처리하는 전용 앱. 기존에는 마트가 자체 기사를 운영하거나 외부 호출 서비스(건당 약 4~6천원)에 의존해야 했고, 이는 배달 관리 비효율과 비용 부담의 원인이 됨. 자사 기사 앱 도입으로 운영 효율을 확보하고 외부 호출 비용을 대체하기 위한 신규 사업으로 진행됨. Android 1명, 백엔드 1명, 기획 1명, 디자인 1명과 협업하며 iOS를 단독으로 담당함.

실시간 주문 동기화 — SSE 기반 상태 일관성 설계

  • 서버 → 클라이언트 단방향 알림만 필요한 도메인 특성을 고려해 SSE 채택. 백엔드팀과 협의하여 결정
  • SSE는 “변경 발생” 신호로 활용하고, 실제 데이터는 API fetch 후 로컬 캐시와 비교해 갱신하는 방식 채택
  • 활성 탭 전략 — 배달대기, 배달중, 배달완료 3개 탭 중 활성 탭에서만 SSE를 처리하고 비활성 탭은 진입 시점에 fetch. 전 탭 처리 시 발생하는 사이드 이펙트와 불필요한 갱신을 차단
  • 스크롤, 정렬 인지 삽입 — 현재 스크롤 위치와 정렬 기준에 따라 신규 주문을 적절한 위치에 삽입. 비활성 탭에는 카운트 dot으로 인지 가능하게 처리. 초기 기획에 없던 요구사항으로, 구현 과정에서 사용성 이슈를 식별해 기획 추가를 제안함

동시성 정합성 — 다중 기사 환경의 주문 선점 처리

  • 한 마트의 여러 기사가 동일 주문을 동시에 잡으려 할 때 발생하는 race condition을 백엔드팀과 함께 정의 및 해결
  • “배달 시작” 액션 시 서버가 선점 가능 여부를 판단하는 구조로 설계. 클라이언트는 응답에 따라 성공, 실패를 분기 처리
  • 성공, 실패와 무관하게 해당 주문을 배달대기 탭에서 제거하고, 카운트 갱신은 별도 fetch로 분리해 응답 페이로드를 최소화

재연결 시 데이터 복구

  • 네트워크 단절 후 첫 SSE 이벤트 수신 시점에 전체 페이지를 재fetch하고 캐시와 비교 동기화
  • 단절 시점에 페이지 사이즈(30개) 이상의 주문 발생 시 누락 가능성을 식별해 팀에 공유. 출시 일정상 후속 과제로 합의

클린 아키텍처 구조 재편 (2026.05~06)

  • SwiftUI 앱을 Presentation / Domain / Data / API / Common 5개 모듈로 물리 분리
  • Domain 레이어의 UI, API 의존 누수를 제거해 도메인 코드가 프레임워크에 의존하지 않는 구조를 확립. 화면을 Screen + ViewModel + Subview로 재구성하고 DI를 컨테이너 기반으로 전환
